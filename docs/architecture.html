Course Review Tool Architecture

A standalone service that takes a course-package zip (Grade 6 Islamiat is the reference sample), runs the Course Review Checklist against it, entirely offline, and returns a filled-in checklist workbook with evidence for every Fail.

Status: architecture for engineering review. All product decisions are recorded in section 11. The checklist workbook is followed as written. It is built at D:\Mediatiz\course_review_tool: command line and a local web page, SLO coverage, model-assisted checks, a textbook index and format learning, with over 150 offline tests. How accurate the model is on Urdu is being measured against a real Ollama host.

1. Context and scope

Reviewers currently fill a spreadsheet by hand: one row per lesson, one column per checklist code (LP1 to LP10, FG1 to FG8, PQ1 to PQ5 and so on), each cell Pass, Fail or N/A. The tool automates as much of that as is defensible and leaves a clearly marked remainder for a person.

Input: what a package looks like

LevelArtifactsFormat
Per lessonLesson Plan, Assessment (6 questions), Video Storyboard, Facilitator Guidedocx, docx, docx, pptx
Per chapterChapter Exam (20 questions)docx
Per subjectPop Quiz (all lessons in one file), Data Bank (multiple versions), Document of Specifications, textbookdocx, docx, docx, pdf

This Grade 6 Islamiat package (126 files, 81 MB, Urdu, right-to-left) is only an example of the input. Nothing in the tool may be hard-coded to it: subject, language, number of chapters and file names all vary. The folder tree is the primary structure signal, but even here it is inconsistent (Chpater-7, Lesson Plan.docx with a space, a Chapter 1 with no lesson folders), so ingest must tolerate that and report what it could not place.

Goals and non-goals

Goals
  • Any subject or grade in this folder shape, not just Islamiat.
  • The checklist workbook is the rule source and is followed as written.
  • Runs fully offline, with a local Ollama as the only model.
  • Every result carries evidence a reviewer can check.
Non-goals
  • Not an authoring tool; it never edits the package.
  • No silent AI Pass. Judgement checks are suggestions.
  • No cloud model and no cloud services.
  • No judgement of subject-matter correctness.

2. System overview

Deterministic

Code reads styles, sizes, counts and structure and can be exact. Page setup, fonts, colour, heading numbering, footers, question counts, section order.

AI judgement

Needs reading comprehension. SLO coverage, scope creep, story continuity, warm-up quality, feedback quality. Returns a suggestion plus quoted evidence.

Reviewer only

Not reliably automatable. Logo placement, screenshots with browser chrome, fidelity to the book. Always emitted as needs_review.

5. Rule engine

The checklist workbook is the rule source. At start-up the engine reads the Key sheet (code, scope, wording) and the matrix sheets (which codes belong to which output), so every report cites the reviewer's own wording and records which workbook version was used. A YAML binding attaches an implementation to each code. A code with no binding is reported as not automated, never skipped silently, and an edited workbook needs no code change unless it introduces a new kind of check.

- code: PQ1
  doc_type: pop_quiz
  target: lesson            # fills the Pop Quiz sheet, one row per lesson
  kind: deterministic       # deterministic | ai | human
  check: question_count
  params: { min: 2, max: 3, allowed_types: [mcq] }
  fail_message: "Lesson {lesson}: {n} questions, {bad_types} not MCQ"

- code: LP1
  doc_type: lesson_plan
  target: lesson
  kind: ai
  check: slo_coverage
  inputs: { slos: spec.slos[lesson], section: concept_building }
  fail_message: "SLO not covered: {slo}"

- code: PQ4
  doc_type: pop_quiz
  target: lesson
  kind: deterministic
  check: correct_answer_highlight
  params: { colour: yellow, accept: [run_highlight, cell_shading] }
  fail_message: "Lesson {lesson}: Q{q} correct option is not highlighted yellow"
  • A check is a pure function from parsed documents and params to a list of Finding. No I/O, so each one is unit-testable against a tiny fixture file.
  • Rules that are unsatisfiable on this package return na with a reason, rather than a false Fail. Example: DB1 when the package has no Data Bank for that lesson.
  • The formatting rules (WE1 to WE25) apply to every document as written, with no language exemption. An Urdu document set in Noto Nastaliq Urdu fails WE7, and a US Letter page fails WE4.
  • "Highlighted" means a real yellow run highlight or yellow cell shading on the correct option. A check-mark emoji beside it fails PQ4 and DB4.
  • Where the team deliberately departs from the workbook, the profile can override a rule parameter. Every override is printed at the top of the report (for example DB1: 4 to 6 items became 5 to 8). No overrides are used today, so the workbook stays the authority and the departure stays visible.
Workbook followed as written. Chapter Exam is per lesson and Worksheet is per chapter, and the Data Bank rule is 4 to 6 MCQ lower-order items per lesson, exactly as the workbook defines them. Files are bound to sheets by scope, not by file name (section 11).

6. AI checks and the agent loop

AI checks run as a bounded tool-using agent per (rule, target). It does not get the whole package in one prompt. It asks for what it needs, answers in a fixed schema, and its quotes are verified by code before anything is stored.

Tools exposed to the agent

ToolReturns
get_rule(code)Checklist wording, scope, and the output schema.
get_slos(lesson)Official SLOs for the lesson from the Document of Specifications.
list_sections(doc)Heading tree with numbering.
read_section(doc, heading)Text of one section, capped in length.
list_questions(doc, lesson)Parsed questions with SLO tags and options.
search(query, scope)Top matching blocks within the lesson or chapter. Never crosses into another subject.
  • Bounded. Step cap and token budget per check; one check cannot run away.
  • Local only. One OllamaClient, pointed at a local Ollama or one shared through an ngrok tunnel. No cloud model is implemented. A deterministic-only mode runs the whole tool with no model at all.
  • Built for a small model. Context is small (about 8k tokens), so checks are chunked per section and the model only ever sees retrieved passages. A multilingual embedding model served by Ollama pre-selects candidate passages for coverage checks (LP1, LP2, PQ5), and the LLM judges those snippets instead of whole documents. Where a model lacks reliable tool calling, the same checks run as a fixed retrieve-then-judge chain; the evidence check is identical.
  • Urdu quality gate. Small local models are likely to be weak at Urdu reading comprehension. Before each rule goes live, run the candidate model on a labelled Urdu sample and measure agreement with reviewers. A rule below the agreement threshold is demoted to needs_review only, with the retrieved passages shown, instead of an AI suggestion.
  • Subject-wide checks (ST1, ST2) are an aggregation over the Question table by SLO tag, which is deterministic once tags are extracted. The AI step only helps extract missing tags.

7. Outputs

Filled checklist (.xlsx)

The reviewer's own workbook: same sheets, same dropdowns, one row per lesson. Fails column recomputed by the existing formula. Notes carry the code and evidence, for example "LP4: heading has no number, section 3". AI suggestions are marked so they are visibly unconfirmed.

HTML report

Summary first (counts by scope and status), then per lesson drill-down with the quoted evidence, a link to the exact source block, and Confirm / Override controls that write Override rows.

JSON

The full findings table plus the package inventory, for pipelines and dashboards. Versioned schema.

The workbook is written by loading the original template with openpyxl and filling cells, so layout, validation lists and formulas are preserved and the template stays editable by the reviewers who own it.

9. Operations, security and testing

Security

  • Zip-slip, zip-bomb and size limits at extract.
  • Files are only parsed, never executed or opened by Office.
  • Per-job workspace, deleted on a retention timer.
  • Documents stay on the machine running the tool. If Ollama is reached through an ngrok tunnel, prompt text passes through ngrok's servers, so protect the tunnel with authentication, or run Ollama on the same network to keep everything internal.

Reliability

  • Parse cache keyed by file hash; re-runs only redo changed files.
  • A failing check yields needs_review with the error, never a crash or a false Pass.
  • Deterministic work runs per lesson in parallel. AI calls run at low concurrency (one shared GPU), with a health check and retry. If the Ollama tunnel is down, AI checks come back as needs_review with the reason, never as Pass.

Testing

  • Unit test per deterministic rule on a minimal fixture docx.
  • The sample zip as a golden package: expected findings checked in.
  • AI checks scored against a human-labelled set; track agreement per rule and gate releases on it.
